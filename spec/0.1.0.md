# Open Archive Format 0.1.0

Status: initial experimental specification. Published 2026-10-30.
This document and the two bundled JSON Schemas are normative. MUST, MUST NOT,
SHOULD and MAY express requirements, prohibitions, recommendations and options.
Schemas define fields, types, required members and enumerations; this document
adds semantics and cross-record rules. Conformance requires both. In a conflict,
this document takes precedence; report an erratum. Examples are informative.

## 1. Scope and conformance

OAF is a vendor-neutral, user-owned interchange format for a digital catalogue.
An OAF archive is a directory containing `manifest.json` and `records.jsonl`.
0.1.0 defines only the `catalogue` profile: source content is external and MUST
NOT be required for reading or validating the catalogue. OAF requires no service,
account, database, operating system, subscription or particular application.
An implementation MAY use any internal storage, including SQLite.

A conforming writer emits both files satisfying every normative requirement.
A conforming core reader validates syntax, schemas and the rules in section 5,
rejects unsupported versions/profiles/required extensions, and interprets core
fields as specified. A reader claiming lossless round-trip MUST preserve all
records, IDs, metadata and optional extension values, including unknown values.
Byte-for-byte JSON formatting and member order need not be preserved. A reader
that cannot preserve unknown data MUST warn before exporting a lossy copy.
The reference validator implements core validation, not importing, editing,
scanning or content verification. A successful result proves neither truth of
claims nor availability, authenticity, privacy or integrity of external content.

## 2. Serialization and manifest

Both files MUST be UTF-8 without BOM; strings MUST contain Unicode scalar values
(no unpaired surrogate escapes). JSON MUST follow RFC 8259: duplicate member
names, NaN and infinities are forbidden, including inside metadata/extensions.
Numbers MUST be finite. Defined integer fields range from 0 to 2^53-1 inclusive.
Metadata producers SHOULD use strings for larger numbers to avoid precision loss.

`manifest.json` is one JSON object. `records.jsonl` contains one compact or
single-line JSON record per line, terminated with LF (CRLF accepted); blank lines
are forbidden. An empty records file is valid. Forward references are allowed;
record order carries no semantics. No record may span physical lines; newlines
in strings use JSON escapes. JSON member order is insignificant. There is no
canonical serialization, signature or byte-level catalogue hash in this version.

The manifest MUST contain:

| Member | Meaning |
| --- | --- |
| `format` | Literal `OAF`. |
| `version` | Exact literal `0.1.0`. Marketing shorthand is “v0.1”. |
| `archive_id` | Persistent UUID URN identifying the catalogue lineage. |
| `created_at` | Time this export was created. |
| `profile` | Literal `catalogue`. |
| `records` | Literal `records.jsonl`; arbitrary paths/URLs forbidden. |
| `required_extensions` | Unique extension keys required to interpret this archive; normally empty. |

`title` and `extensions` are optional. Other manifest members are forbidden.
The archive ID remains stable across exports of the same catalogue lineage;
a deliberately forked independent catalogue MUST receive a new archive ID.
It is not a digest of the export. Unrelated catalogues MUST NOT reuse it.
Additional directory members are outside this profile and MUST NOT be interpreted
as OAF content, scripts or restoration instructions. Readers MUST NOT traverse
paths or fetch links merely because they appear in a catalogue.

All core timestamps MUST be RFC 3339 UTC strings ending in uppercase `Z`, with
seconds 00–59 and optional fractional seconds of 1–6 decimal digits. Unknown times are omitted where
optional. Writers MUST NOT invent original observation times; an import activity
can record the import time. For unknown original observation time, use the time
of the import observation and explain that limitation in metadata. `mtime` is
observed modification time, not a claim of authorship or original creation.

## 3. Identity and record model

Every record has a `type` and an `id`. All record IDs and archive IDs MUST use
lowercase `urn:uuid:` followed by canonical lowercase UUID hex groups 8-4-4-4-12.
Writers SHOULD generate random UUIDv4 identifiers and MUST avoid collisions.
Examples use fixed synthetic IDs. IDs MUST NOT embed paths, email addresses,
provider account IDs, device numbers, inodes or other private identifiers.
UUIDs are opaque identifiers; they do not prove identity, ownership or authenticity.

Record IDs MUST be unique across all record types within an archive and MUST
not equal its archive ID. Preserve IDs when exporting the same entities. Never
reuse an ID for a different entity. If records with the same ID conflict during
merging, implementations MUST surface the conflict and preserve both inputs;
last-writer-wins and automatic remapping are not defined by OAF 0.1.0.

### 3.1 Source

A source is an origin collection, not an account and not a mounted path.
Required: `label` (human-readable), `source_kind` (`local`, `remote`, `removable`,
`other`). A source ID MUST remain stable through an explicitly confirmed move or
remount of that same collection. Device/inode pairs, provider IDs and paths are
implementation hints only and MUST NOT establish portable identity by themselves.
A replacement collection MUST receive a new ID unless the user confirms continuity.
Core has no account record, root locator, credentials or automatic rebind operation.
Actual access configuration belongs in a separate private application store.

### 3.2 Occurrence

An occurrence is one historical observation of an object in a source. Required:
`source_id`, `kind`, `observed_at`, `state`, `activity_ids`. It is immutable:
a later observation MUST have a new ID, even if the location appears unchanged.
An exact re-export retains the original ID. This permits partial and historical
catalogues without pretending that a scan is an atomic filesystem snapshot.

`kind` is `file`, `directory`, `package`, `symlink`, `special` or `unknown`.
A package is an opaque application/library container; its internal objects and
aggregate size are unknown unless a later explicit profile specifies otherwise.
`state` is `present`, `missing`, `inaccessible` or `unknown`. Missing means the
producer explicitly observed absence at this location, not that content has been
destroyed. Inaccessible means observation failed; unknown means no reliable
presence claim. Absence from an export MUST NOT imply deletion or missing state.
A partial activity MUST NOT be interpreted as complete source coverage.

Optional `path_segments` are source-relative logical location components, in
order. Omission means withheld/unknown; `[]` explicitly means the source root.
Components MUST be nonempty, MUST NOT be `.` or `..`, and MUST NOT contain slash,
backslash or NUL. They are literal labels, never URL-decoded or expanded.
Writers MUST NOT normalize case or Unicode to infer equality. Names that cannot
be represented faithfully MUST be omitted, with an explanatory metadata note;
a future encoding profile may address raw filesystem bytes. Readers MUST NOT
join these segments to a host path for automatic reads or writes. Two sources
with the same relative location are still distinct origins. Repeated observations
of one location are valid; no rename, hardlink or path-identity inference is implied.

`size_bytes` is optional and allowed only for present regular files; zero is a
known empty file, omission is unknown. `mtime` is optional. `asset_id` is optional
and allowed only for regular files. A missing occurrence MAY retain an earlier
verified asset association; it MUST NOT claim a current file size. An occurrence
without an asset is fully valid and does not imply that its content was opened.

### 3.3 Asset

An asset identifies a particular byte sequence independently of source/location.
Required: `activity_ids`. Optional: `sha256`, `size_bytes`, `media_type` (a media
type token without parameters). Core does not model directory or package digests.
An asset ID MUST NOT be reused for changed bytes. Asset identity MUST NOT be
inferred solely from names, size, timestamps, inode, provider IDs or similarity.
If no reliable byte-identity evidence exists, omit `asset_id` and usually omit
an asset record. Hashless assets MAY express an explicit, provenance-backed
producer assertion; readers MUST treat them as unverified assertions.

`sha256`, if present, is 64 lowercase hex characters for SHA-256 of the complete
unmodified file byte stream. Producers MUST actually compute or import documented
hash evidence before making this claim and MUST attach a completed `hash`
activity. Imported evidence SHOULD identify its method in metadata, without
publishing private identity or access information. SHA-256 supports identity
comparison, not trust, signatures, malware safety or ownership. Readers MAY
suggest matching verified digests but MUST NOT destroy or merge original files
on this basis. Distinct asset IDs with the same digest are allowed; known sizes
for that digest MUST agree. Occurrence and linked asset sizes MUST agree when
both are present. This validator checks claims, not the underlying bytes.

### 3.4 Activity and provenance

An activity records an observation, import, assertion or hashing event. Required:
`action` (`observe`, `import`, `assert`, `hash`), `started_at`, `source_ids` (unique,
possibly empty), `outcome` (`completed`, `partial`, `failed`). Optional: `ended_at`,
`agent` (non-secret software/tool description). End MUST NOT precede start.
Completed means that activity completed its declared scope, not necessarily the
whole source. Scope/limitations SHOULD be described in metadata. A failed or
partial activity can support the observations it actually made.

Every occurrence, asset and annotation MUST cite at least one activity through
`activity_ids`. At least one activity cited by an occurrence MUST list that
occurrence's source. Activities reference sources, not occurrences; this avoids
circular causal records. An activity is a producer statement, not an audit
signature. Source registration itself has no mandatory activity in 0.1.0.
There is no causal graph, detailed per-field evidence, custody transfer or
cryptographic chain of custody in this version.

### 3.5 Annotation

An annotation attaches user/producer commentary to a source, activity, asset or
occurrence. Required: `target_id`, `body` (nonempty plain text), `activity_ids`.
Optional: unique string `tags`. Annotation-to-annotation links are forbidden.
An annotation is an attributed claim, not a replacement for measured metadata.
Readers MUST render its body as untrusted text, not executable HTML or commands.
Use a new annotation ID for a revised annotation; deletion/edit history and
supersession semantics are future work. Personal author identities are optional
private application information, not a required field.

## 4. Metadata and extensibility

Every record MAY include `metadata`, an arbitrary JSON object for descriptive
information (for example `title`, `description`, `language`, `rights`), with no
standardized semantics in 0.1.0. Producers SHOULD document conventions. Metadata
MUST NOT override core fields, identity, validation or extension negotiation.
Metadata is not a content payload channel; this profile MUST NOT embed original
file contents in metadata, annotations or extensions.

Every record and the manifest MAY include `extensions`, a JSON object whose
keys are absolute HTTPS namespace identifiers with a nonempty fragment, such as
`https://example.org/oaf#colour`. The namespace SHOULD be controlled by its author.
Keys identify semantics and need not resolve; readers MUST NOT fetch them while
validating. Values may be any finite, valid JSON. Unknown optional extensions
MAY be ignored for interpretation but MUST be preserved for lossless round-trip.
Unknown required extensions MUST stop interpretation/import, never be silently
ignored. Generic structure may still be inspected as untrusted data.

`required_extensions` lists unique keys whose semantics are essential anywhere
in the archive. An extension-aware implementation MUST implement those semantics
and validation before claiming full conformance. The reference validator supports
no required extensions and rejects every nonempty list. Optional extensions
cannot modify core semantics; a feature needing that change needs a future
version/profile. Unknown core members and unknown record types are invalid;
new private fields belong inside metadata or extensions.

## 5. Whole-archive validation

In addition to schemas and serialization, validators MUST check unique record
IDs and archive/record ID separation, resolve every reference within the archive,
and enforce the following target types:

| Reference | Required target |
| --- | --- |
| occurrence.source_id, activity.source_ids[] | source |
| occurrence.asset_id | asset |
| asset/occurrence/annotation.activity_ids[] | activity |
| annotation.target_id | source, activity, asset or occurrence |

External/dangling references are forbidden in this version. Validators MUST also
check activity time ordering, occurrence source provenance, allowed size/asset
placement, linked sizes, digest-size consistency, completed hashing provenance
for digests, supported version/profile and required-extension support. They MUST
NOT require network access, mount sources, scan content or mutate any originals.
A structural-only JSON Schema check is necessary but insufficient for conformance.

## 6. Safety, privacy and non-destructive behavior

Catalogue-only does not mean non-sensitive. Locations, annotations, hashes,
titles, timestamps and extension values may disclose private information.
Exporters SHOULD offer a preview and explicit redaction controls. For public
sharing, omit locators and private account mappings, replace labels, remap IDs
consistently if necessary, remove descriptive/private metadata and retain only
safe provenance. Redaction MUST NOT leave dangling references or invent evidence.
If hash provenance cannot safely be retained, omit the digest claim. OAF grants
no licence to the user's content or catalogue; repository licences cover only
this specification and shipped reference materials.

Importers MUST treat all values as untrusted data, MUST NOT execute catalogue
values or fetch URLs automatically, and MUST NOT modify, relocate or delete
source content as an effect of reading/importing OAF. User-selected actions
outside interchange require separate explicit authorization. Readers SHOULD
bound file sizes, record lengths/counts, JSON nesting and memory consumption and
report resource limits separately from semantic invalidity. The reference tool
limits a line/manifest to 8 MiB and combined input to 128 MiB, loads records into
memory, and rejects symlink members. Those are tool limits, not format limits;
very large catalogues need another implementation. It reads only the two fixed
members; no archive extraction, URI resolution or content opening is implemented.

## 7. Versioning and compatibility

Version strings are MAJOR.MINOR.PATCH. 0.1.0 is an experimental initial contract;
0.x minor releases MAY break compatibility and MUST document migration rules.
For 1.0 and later, major versions mark breaking changes; minor versions add
compatible optional features; patches clarify/correct without changing accepted
instances or semantics. Because 0.1.0 schemas are closed, adding core members
requires a new supported version. Readers MUST explicitly support the declared
version and MUST NOT guess compatibility from a shared major version. A future
reader can support several schemas; an older reader rejects newer versions.
Required extensions provide explicit negotiation, never implicit compatibility.

Published versioned specs/schemas MUST remain immutable. Corrections ship in a
new version; changelogs explain their impact. A format version is distinct from
a tool release and from export creation time. Migrations MUST preserve original
input, produce a new export, document lost/changed semantics, and retain IDs for
unchanged entities. No migration or merge tooling is implemented in 0.1.0.

## 8. Future work — not specified or implemented

Optional self-contained content packages (potential `content` profile), content
manifests, safe extraction, package-directory hashing, signatures, encryption,
compression, thumbnails/OCR, relationship/derivation graphs, raw filename bytes,
streaming validation, formal extension registries, scanner/provider adapters,
SQLite importer/exporter, source rebind tools, conflict resolution and automatic
synchronization are future work. No reserved profile or extension here promises
those capabilities. A catalogue is not a backup and cannot restore missing bytes.
